# LibreOffice AI Agent 架构说明

英文版: [libreoffice-ai-agent-architecture.md](./libreoffice-ai-agent-architecture.md)
详细 MVP 设计规格: [libreoffice-ai-agent-mvp-design-spec.zh-CN.md](./libreoffice-ai-agent-mvp-design-spec.zh-CN.md)

## 概述

这份文档说明了 LibreOffice AI 聊天与代理系统的目标架构。

第一阶段，这个系统只支持 Windows，并且先以“独立兄弟仓库”的方式交付，而不是一开始就直接改 LibreOffice 核心代码。它会通过两个部分集成到 LibreOffice 中：

- 一个 LibreOffice 扩展
- 一个本地侧车进程（sidecar，也就是运行在 LibreOffice 外部、专门负责 AI 能力的辅助程序）

系统目标是：让用户在 LibreOffice 里通过聊天面板调用 Writer、Calc、Impress 的常见功能，同时保证修改过程安全、可撤销、注意隐私，并且不被某一家 AI 供应商绑定。

## 固定产品决策

- 第一阶段应用范围：Writer + Calc + Impress
- 交付方式：先做独立扩展和侧车仓库，放在 LibreOffice core 旁边
- 默认隐私策略：默认只发送“当前选中内容”给模型
- 凭证方式：用户自己提供 API Key，也支持本地开源模型端点
- 本地模型策略：支持任何 OpenAI 兼容接口的本地服务
- 平台范围：仅 Windows
- 第一阶段明确不做：宏生成和宏执行
- 审批策略：安全的纯格式操作直接执行；更大的内容修改先预览，再确认
- 历史记录策略：会话历史按“文档 + LibreOffice 配置目录（profile）”分别保存

## 目标

- 在 LibreOffice 内提供一个感觉自然、像原生功能一样的 AI 聊天面板
- 在不改 LibreOffice 端代码的前提下支持多个模型供应商
- 通过“类型化工具”执行高置信度办公操作，而不是脆弱的 UI 自动点击
- 让写入操作足够安全、明确，并且容易撤销
- 在 Writer、Calc、Impress 之间复用同一套代理调用契约

## 非目标

- 第一阶段不追求“AI 完全自动控制 LibreOffice 的全部功能”
- 不做基于界面点击的原始 UI 自动化
- 第一阶段不做宏编写或宏执行
- 第一阶段不做跨平台支持
- 在扩展 MVP 还没证明可行前，不直接把系统深度合并进 LibreOffice core

## 术语说明

- OXT：LibreOffice 扩展安装包格式，可以理解为 LibreOffice 的插件包。
- 侧车进程（sidecar）：与主程序配套运行、但不直接嵌入主程序内部的本地辅助进程。
- UNO：LibreOffice 的核心组件接口和命令调用体系。很多功能最终都要通过它来访问。
- 命名管道（named pipe）：Windows 本地进程之间通信的一种方式。它比默认开启一个本地 HTTP 端口更收敛，也更适合同机进程通信。
- 动作注册表（action registry）：一张“AI 允许调用哪些能力”的清单，是系统安全边界的核心。

## 架构原则

1. AI 厂商相关逻辑放在 LibreOffice 外部，不写死到 LibreOffice 里。
2. 只暴露“明确、可验证的办公能力”，不暴露任意内部访问能力。
3. 默认只发送最少的文档上下文。
4. 只要是比较重要的写操作，都必须能检查、能撤销。
5. 先把范围做窄、做稳，再扩展命令覆盖率。

## 主要组件

### 1. LibreOffice 扩展

扩展负责 LibreOffice 进程内的行为。

职责：

- 注册 AI 聊天用的侧边栏 deck 和 panel
- 显示对话内容、动作预览、Provider 状态和用户确认提示
- 通过 UNO 和更高层文档 API 读取当前文档上下文
- 通过工具注册表执行已批准的动作
- 用“可安全撤销”的方式应用修改
- 在 LibreOffice profile 中保存按文档区分的历史记录
- 启动并连接本地侧车进程

初始实现语言：

- 通过 `pyuno` 使用 Python

原因：

- 扩展侧迭代速度最快
- 很适合第一阶段的 UNO 集成和侧车通信契约
- 可以避免把变化很快的 AI SDK 代码塞进 LibreOffice core

### 2. 本地 AI 侧车进程

侧车进程是由扩展按需启动的本地外部程序。

职责：

- 读取 Provider 配置和模型目录
- 管理 API 凭证和本地端点设置
- 统一不同 Provider 的请求和返回格式
- 把模型输出以流式方式发回扩展
- 把用户意图转换成结构化工具提案
- 在输出工具提案前先做策略检查
- 生成结构化计划和动作卡片，而不是直接做自由式自动化

侧车进程本身不直接改 LibreOffice 文档。

### 3. Provider 适配层

Provider 适配层全部放在侧车进程中。

支持的适配器类型：

- OpenAI 兼容 HTTP 适配器
- Anthropic 适配器
- Gemini 适配器
- OpenRouter 适配器

第一阶段里，本地模型优先走 OpenAI 兼容接口。

例如：

- 本地 LM Studio 端点
- 本地 vLLM 端点
- 本地 text-generation web UI 端点
- 暴露 OpenAI 兼容 API 的本地 llama.cpp server

### 4. 动作注册表

动作注册表是系统最关键的安全边界。

每个动作都必须是：

- 有名字的
- 有明确类型的
- 有作用范围限制的
- 有参数校验的
- 最终映射到 UNO 命令、文档 API，或者少量可控的多步骤办公流程

示例：

- `Writer.GetSelection`
- `Writer.ReplaceSelection`
- `Writer.ApplyParagraphStyle`
- `Writer.ToggleBold`
- `Calc.GetSelectedRange`
- `Calc.InsertFormulaInSelection`
- `Calc.CreateChartFromSelection`
- `Impress.GetSelectedText`
- `Impress.CreateSlideFromOutline`
- `Impress.ApplyLayout`
- `App.ExecuteUnoCommand`

`App.ExecuteUnoCommand` 也只能基于白名单使用。模型不能获得“任意命令执行权”。

### 5. 上下文提取器

上下文提取器负责把当前办公状态压缩成紧凑、结构化的数据。

Writer 上下文：

- 当前选中文本
- 段落和样式元数据
- 光标位置摘要
- 文档语言和文档类型

Calc 上下文：

- 当前选中地址范围
- 选中范围内可见值或公式
- 工作表名称
- 数字格式元数据

Impress 上下文：

- 当前选中文本或对象
- 幻灯片编号和布局
- 是否有备注

第一阶段默认策略：

- 只把当前选中内容发给模型

逐步升级范围的路径：

- 当前段落
- 当前形状或当前幻灯片局部区域
- 当前选区周边范围
- 明确征得同意后的整篇文档或整张工作表范围

### 6. 对话与历史记录存储

历史记录会按文档保存在当前 LibreOffice profile 中。

主键模型：

- profile id
- 标准化后的文档 URL
- 应用类型

保存的内容包括：

- 用户提问
- 模型响应
- 工具提案
- 已批准的工具执行记录
- Provider 和模型元数据
- 用户同意事件

历史记录里不应保存原始 API Key。

## 交互模型

### 聊天界面

推荐的 UI 是侧边栏面板。面板头部要清楚显示：

- 当前 Provider
- 当前模型
- 当前隐私范围提示
- 侧车是否已连接

### 动作语义

动作分为四类，这四类决定是否自动执行。

| 类别 | 例子 | 审批方式 |
|---|---|---|
| 只读 | 总结选区、解释公式 | 立即执行 |
| 安全的纯格式操作 | 加粗、标题、项目符号样式、对齐 | 立即执行 |
| 内容编辑 | 改写段落、插入摘要、生成幻灯片文字 | 预览后确认 |
| 破坏性或大范围操作 | 大范围替换、覆盖式排序、删除内容 | 预览后明确确认 |

### Undo 契约

所有写操作都必须做好分组，让用户可以用可预期的方式撤销。

## 数据流

### 启动流程

1. 用户打开 LibreOffice。
2. 用户打开 AI 面板时，扩展按需启动。
3. 如果侧车还没运行，扩展启动侧车。
4. 扩展和侧车通过命名管道完成握手。
5. 扩展加载 Provider 设置和该文档对应的历史记录。

### 标准请求流程

1. 用户在聊天面板输入问题。
2. 扩展抓取“只包含当前选区”的上下文。
3. 扩展把请求封装后发给侧车。
4. 侧车选择 Provider 和模型。
5. 侧车返回两类结果之一：
   - 直接只读回答
   - 一个或多个结构化工具提案
6. 扩展判断提案属于哪一类动作。
7. 扩展对安全的纯格式操作直接执行；对较大编辑操作先显示预览。
8. 扩展执行已批准工具，并记录结果。
9. 扩展更新对话线程并保存历史记录。

## 通信方式

Windows 第一阶段采用：

- 命名管道

原因：

- 默认不需要开启本地 HTTP 监听端口
- 很适合同机的扩展和侧车通信
- 可以减少被其他本地进程误用的风险

## 设置模型

### 扩展侧设置

- 开启哪些应用：Writer、Calc、Impress
- 隐私默认策略
- 是否自动应用安全格式操作
- 本地历史记录保留上限
- 日志详细程度

### 侧车侧设置

- 启用哪些 Provider
- Provider 凭证或本地端点 URL
- 默认远程模型
- 默认本地模型
- 请求超时时间
- token 预算和成本控制

敏感信息建议存储在 Windows Credential Manager 或加密后的 profile 作用域存储中。

## 安全与隐私

- 默认只发送选区上下文
- 整篇文档上下文必须显式征得用户同意
- 第一阶段不执行宏
- 第一阶段不开放任意 shell 或文件系统工具
- 不开放无限制的 UNO 命令执行
- 审批和执行都要有审计记录
- 每次请求前，UI 中都要明确显示当前 Provider

## 命令与能力来源

最初的动作注册表应该来自 LibreOffice 已有的命令元数据和文档 API。

主要来源：

- `GenericCommands.xcu`
- `WriterCommands.xcu`
- `CalcCommands.xcu`
- `DrawImpressCommands.xcu`

这些文件能提供标签和命令标识，但代理层仍然需要额外定义“更高层、更适合 AI 理解”的动作。

## 阶段计划

### Phase 0：技术验证

- 证明扩展可以正确打包
- 证明侧边栏面板可以成功注册
- 证明命名管道侧车握手可以正常工作
- 证明一个 Writer 只读工具和一个 Writer 格式工具可以跑通

### Phase 1：Writer MVP

- 侧边栏聊天面板
- Provider 选择
- 本地 OpenAI 兼容端点支持
- 远程 Provider 支持
- 只发送选区上下文
- 安全格式操作自动应用
- 内容编辑预览并确认
- 按文档保存会话历史

### Phase 2：Calc MVP

- 选中区域提取
- 公式解释和插入
- 基于选区创建图表
- 安全格式和数字格式工具

### Phase 3：Impress MVP

- 选中文本和对象提取
- 幻灯片内容改写
- 根据提纲生成幻灯片
- 布局类动作

### Phase 4：更广覆盖

- 更大的白名单命令注册表
- 更好的意图到动作路由能力
- 更丰富的跨应用多步骤流程

## 主要风险与应对

### 风险：侧边栏扩展注册比预期更慢

应对：

- 让动作契约不依赖某一种 UI 承载方式
- 如果必要，先临时退回到无模式停靠窗口或启动器式 UI

### 风险：自然语言请求不容易准确映射到命令级动作

应对：

- 先建立经过筛选的高层动作注册表
- 先选高层动作，再映射到底层命令

### 风险：不安全或出乎意料的修改会降低用户信任

应对：

- 只有安全的纯格式操作才自动执行
- 更大的编辑必须先预览
- 永远提供可撤销能力

### 风险：Provider 变化太快，导致系统不稳定

应对：

- 把 Provider 代码隔离在侧车中
- 保持扩展到侧车的通信契约稳定

## 推荐的 MVP 质量标准

第一版只有在下面这些点都稳定时，才算真正可用：

- 能连接一个远程 Provider 和一个本地 OpenAI 兼容端点
- 能读取 Writer 当前选区
- 能总结和改写选中文本
- 能立即应用安全格式操作
- 能对更大的内容修改显示预览
- 能保存按文档区分的会话历史
- 能稳定撤销已应用的修改

如果这条最小链路还不稳定，就不应该急着扩展到 Calc 和 Impress。
